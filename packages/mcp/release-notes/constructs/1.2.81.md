## Changes

- New `githubOidcSubjects` helper returning both GitHub OIDC `sub` patterns for
  a repository or an organization: the plain `repo:<org>/<repo>:*` and the
  id-embedded `repo:<org>@<org-id>/<repo>@<repo-id>:*`.
- `JaypieGitHubDeployRoleProps.repoRestriction` widens from `string` to
  `string | string[]`. The derived default now emits both patterns.
- New `organizationId` prop on `JaypieGitHubDeployRole`, also read from
  `CDK_ENV_REPO_ORGANIZATION_ID` or `PROJECT_REPO_ORGANIZATION_ID`. Unknown ids
  are wildcarded rather than omitted.
- `JaypieWebDeploymentBucket` gains the same `organizationId` and
  `repoRestriction` props and applies the two-pattern default to
  `DestinationBucketDeployRole`, which previously had no override at all.

## Motivation

GitHub issues newer repositories an id-embedded OIDC subject:

    repo:finlaysonstudio@162184378/finlaysonstudio-mockpay@1339091097:environment:sandbox

Older repositories still present the plain form, and a repo-level subject
template does not remove the ids. A trust policy matching only the plain form
rejects a newly created repository with `Not authorized to perform
sts:AssumeRoleWithWebIdentity` (issue #506).

A GitHub name cannot contain `@`, so the wildcard `repo:acme@*/*:*` can only be
satisfied by the organization named `acme`; a similarly named organization does
not match. Supplying `organizationId` pins the pattern.

## Migration

- No action required. Existing deployments gain the second pattern on the next
  deploy; the plain pattern is unchanged.
- Consumers who worked around this by passing both patterns explicitly can drop
  the override, or keep it and pin the organization id instead.
