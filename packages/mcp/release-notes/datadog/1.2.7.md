## Changes

- **`datadogService` is now exported from `@jaypie/datadog`** (#512). The unified
  Datadog query surface (`logs`, `log_analytics`, `monitors`, `synthetics`,
  `metrics`, `rum`, `validate`) moved out of `@jaypie/mcp/suite`. Register it with
  an LLM toolkit through `fabricTool({ service: datadogService })` or with an MCP
  server through `suite.register(datadogService)` without taking the MCP suite and
  its skill files as a dependency.
- **Keys resolve through `getEnvSecret`** (#513). `resolveDatadogApiKey` and
  `resolveDatadogAppKey` read a `SECRET_<NAME>` or `<NAME>_SECRET` reference from
  Secrets Manager at call time and fall back to the plain environment variable.
  Nothing has to be written into `process.env` by the caller first. The existing
  `DATADOG_API_KEY_ARN`, `DD_API_KEY_SECRET_ARN`, and `SECRET_DATADOG_API_KEY`
  variables keep resolving through `getSecret` so a non-Lambda consumer is
  unaffected.
- **Jaypie errors from the service** (#516). Missing credentials throw
  `ConfigurationError`; an unknown command or a missing required parameter throws
  `BadRequestError`. An unsuccessful Datadog response is no longer a throw: the
  result carries `success: false` and a status-specific `error`, so a model
  reading the tool output can explain a 403 rather than losing the call to an
  exception.
- `validateDatadogSetup` now counts a `SECRET_*` reference as a present key.
- `DATADOG.ENV` gained the application key names; `DATADOG_HELP` and the service
  result types are exported.

## Migration

`getDatadogCredentials()` is now async. Await it.
